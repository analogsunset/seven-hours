# REBUILD.md

How to rebuild this project from the data already on disk.

This is a reconstruction spec, not a tutorial. It covers the twelve steps
`run_pipeline.py` actually runs, the decisions already settled by measurement so
they need not be re-argued, and the defects known to exist as of 2026-09-08.

Everything else in this directory — the older numeric SQL, the calibration
studies, forty-odd loose intermediates — is described in §12 and §13.

---

## 1. What this is

431 North American ski resorts, scored against Open-Meteo's ERA5 reanalysis
archive from **1999-06-01 to 2026-05-31** — 27 hourly weather variables, 27
winters. Each resort-day between Dec 1 and Apr 30 is reduced to the seven hours
the lifts turn (09:00–15:00 local) and sorted into **Meh / Good / Great / Epic**.
The result ships as one static HTML file with the entire dataset packed inside
it, no server and no network calls.

Current build:

| | |
|---|---|
| Resorts in reference | 431 |
| Resorts with hours loaded | 431 |
| Resorts shown on the page | 154 (vertical ≥ 899 ft, seven western regions) |
| `meteo.HourlyObs` rows | 102,012,528 |
| `meteo.SkiDay` rows | 4,250,522 |
| SNOTEL station-days | 3,536,299 across 408 stations |
| Database size | ~40 GB |
| Page | `seven_hours.html`, 10.4 MB |
| Full rebuild | ~86 min |
| Export-only rebuild | ~0.7 min |

The page's own self-description — resort counts, hour counts, year span — is
generated, never typed. See §10.

## 2. Prerequisites

- **SQL Server 2022**, server `NESO2`, database `SKI_RESORT`, Windows
  authentication (`sqlcmd -E`). The database must exist; `h00_reset.sql` drops
  objects, not the database.
- The project lives at `D:\TFS\JTDEV\python\ski_resort_stats`, a subdirectory
  of a larger git repository rooted at `D:\TFS\JTDEV`. Absolute paths are baked
  into the BULK INSERT statements (§12).
- **SIMPLE recovery model.** The hourly load loop depends on it (§4).
- **Python 3**, standard library only. There are no third-party imports
  anywhere in this project.
- **Node**, for `_hverify.js`.

### Memory

SQL Server on this box shares 31.5 GB with a WSL2 VM. A destructive run has
already died at error 802 (insufficient buffer pool memory) with the schema
half-dropped, because the VM had ballooned to 14 GB.

`run_pipeline.py:preflight()` therefore checks `sys.dm_os_sys_memory` **before**
anything irreversible happens and refuses to start a destructive run with less
than **1536 MB** free. Refusing costs a rerun; stopping halfway costs the
database.

`wsl --shutdown` reclaims the memory, but it also stops any fetch in flight.
`--skip-reset` rebuilds the model in place without dropping anything.
`--force` overrides the guard.

## 3. Inputs on disk

| Input | What it is | Regenerated by |
|---|---|---|
| `ski_resort_stats_2026.csv` | 431 resorts, 29 pipe-delimited columns, **LF-terminated**. The source of truth for resort identity. | Hand-maintained |
| `json/hourly/*.json` | 431 files, ~15 GiB total, named `<safe_stem>_19990601-20260531.json` | `h01_fetch.py` |
| `_snotel_all.txt` | Daily record for every mapped SNOTEL station | `h19_snotel_all.py` |
| `_snotel_map_all.txt` | Resort → station neighbourhood with distance and elevation delta | `h19_snotel_all.py` |

**Excluded from everything:** `json/hourly/archive/`, and any `cache` folder.

SNOTEL is not re-fetched during a rebuild. Those two text files come from the
NRCS API and have nothing to do with the Open-Meteo side.

### The resort CSV

Pipe-delimited, no quoting, 29 columns in this order:

```
resort_name|state|region|postal_code|summit|mid_elevation|base|vertical|lifts|
runs|acres|green_percent|green_acres|blue_percent|blue_acres|black_percent|
black_acres|lat|lon|mid_elevation_meters|timezone|country|ticket_currency|
peak_day_ticket_local|peak_day_ticket_usd|advance_day_ticket_local|
ticket_basis|map|openmeteo_hourly_api_call
```

Resort names use the `Name - ST` convention (`Alta - UT`). This changed once from
`Alta, UT` and broke every join in the older pipeline, which is why
`h00_reset.sql` exists.

**The file must be LF-terminated.** Excel re-saves it as CRLF. Because
`h03_reference.sql` sets `ROWTERMINATOR = '0x0a'`, a CRLF file leaves a stray
`CR` on the last field of every row — which is the API URL — and would put a
carriage return inside every fetch URL. h03 strips it:

```sql
UPDATE stg.ResortCsv
SET openmeteo_hourly_api_call = REPLACE(openmeteo_hourly_api_call, CHAR(13), '')
WHERE openmeteo_hourly_api_call LIKE '%' + CHAR(13) + '%';
```

That guard only covers the **last** column. Reordering the CSV moves the hazard
to whatever ends up last.

## 4. The pipeline

`run_pipeline.py` runs twelve steps:

```
h00_reset.sql  →  h01_schema.sql  →  h03_reference.sql
      →  h02_shred.py  →  h04_load_hourly.sql
      →  h20_snotel_all.sql   (pass 1: consensus)
      →  h05_skiday.sql       (the model)
      →  h20_snotel_all.sql   (pass 2: score the model)
      →  h14_export.sql  ×3 batches
      →  h07_pack.py  →  _hverify.js  →  h15_build.py
```

### Modes

```bash
python run_pipeline.py "Showdown - MT" "Steamboat - CO"   # smoke test, 2 resorts
python run_pipeline.py --all                              # every json file
python run_pipeline.py --all --skip-reset                 # keep the schema
python run_pipeline.py --all --force                      # ignore the memory guard
python run_pipeline.py --export-only                      # page only, ~0.7 min
```

Bare arguments are **file stems** — the hourly filename minus its
`_YYYYMMDD-YYYYMMDD.json` suffix — passed to `h02_shred.py`. Everything
downstream follows the data: `ref.Resort` always holds all 431, but
`ResortBenchmark`, `SkiDay` and the export only ever cover resorts with hours
loaded. A two-resort smoke test therefore exercises the same code the full build
runs, not a parallel copy.

`--export-only` is the loop for anything downstream of the model — filters,
prose, packing, page markup. **0.7 minutes against 86.**

### Things that are invisible from the code

**h20 runs twice, and the cycle is real.** `meteo.SnotelBenchmark` scores the
model against the gauges, so it reads `meteo.SkiDay`. But `usp_BuildSkiDay`
reads `meteo.SnotelConsensus`, which h20 builds. Pass 1 builds the consensus and
leaves the benchmark empty behind a guard:

```sql
IF OBJECT_ID('meteo.SkiDay', 'U') IS NULL
BEGIN
    PRINT 'meteo.SkiDay does not exist yet -- SnotelBenchmark left empty.';
    PRINT 'Run h05_skiday.sql, then re-run this script to score the model.';
END
ELSE ...
```

h05 then builds the model against the consensus, and pass 2 fills in the kappa
and recall the resort cards print. There is no third pass: `SkiDay` never reads
the benchmark.

**h04 validates against `#Meta` (431 rows), never `stg.HourlyRaw` (102M).** An
`IF EXISTS` against the fact table gives the optimizer a row goal of 1, which it
serves with a nested-loop anti-join that rescans `ref.Resort` per row: 22 billion
inner rows, **37 minutes**. The guarantee is identical against `#Meta`, because
every staged row came from a file that wrote exactly one `#Meta` line.

**h04 loads one resort at a time with a `CHECKPOINT` per iteration.** A single
`INSERT...SELECT` for all 431 is one transaction, and SIMPLE recovery cannot
truncate a log mid-transaction — the log would grow tens of GB. Batched, it
stays flat at 46 MB.

**The clustered index on `stg.HourlyRaw` is created in h04, after the bulk
load**, not in `h01_schema.sql`. Load then index.

**Every SQL file needs `SET ANSI_NULLS ON; SET QUOTED_IDENTIFIER ON;`** — the
computed columns and indexed views require it.

**sqlcmd batches do not share variables.** `@MinVerticalFt` and `@Regions` are
re-declared in all three `h14_export.sql` batches. `h07_pack.py` asserts the
resort-card count equals the count in the meta row, so a drift between the three
declarations fails the build instead of shipping cards with no days behind them.

**`sql_export()` splits on `GO`** and runs each `SELECT` batch into its own file
with `-h -1 -W -w 8000`. The `-w 8000` matters: without it, long trail-map URLs
wrap and break `h07_pack.py`'s field-count check.

## 5. Schema

Three schemas: `ref`, `meteo`, `stg`.

### Tables

| Table | Role |
|---|---|
| `ref.WeatherCode` | 27 WMO codes → description + precipitation type |
| `ref.Resort` | 33 columns; identity, terrain, elevation, prices. `Grid*` filled by the load |
| `ref.ResortSnotel` | Resort → station, with `DistanceKm`, `ElevDeltaFt`, `StationRank`, `ElevRank` |
| `meteo.SourceFile` | One row per loaded JSON file; unique on `ResortId` |
| `meteo.SourceFileUnit` | Per-file, per-variable unit text straight from the JSON |
| `meteo.HourlyObs` | The fact table, 102M rows |
| `meteo.SkiDay` | The model output, one row per resort-day |
| `meteo.ResortBenchmark` | Per-resort snow lines in model inches (`Snow24Cut2In`, `Snow24Cut4In`, `Snow168Cut5In`) plus `CoverCutFt` |
| `meteo.SnotelStationDaily` | Raw gauge record, `(Triplet, ObsDate)` |
| `meteo.SnotelConsensus` | Neighbourhood composite per resort-day |
| `meteo.SnotelBenchmark` | Model-vs-gauge scores per resort |
| `stg.HourlyRaw`, `stg.ResortCsv`, `stg.SnotelAllRaw`, `stg.SnotelMapAllRaw` | Bulk-load staging |

### Views

`meteo.vSkiDay`, `meteo.vSkiDaySnow` (both owned by `h05_skiday.sql`),
`meteo.vSnotelStationDay` (owned by `h20_snotel_all.sql`).

`vSkiDaySnow` is what the export reads. It adds `Visibility`, `SnowSource`,
`GaugeCount`, `NearestKm`, `SnotelSwe72Rel` and `SnotelIsFresh` to `d.*`. Both
views select `d.*`, so a new `SkiDay` column flows through without touching them.

### `meteo.HourlyObs`

29 stored columns, all `NOT NULL`, plus three **PERSISTED computed** columns:

```sql
SeasonStartYear AS (CASE WHEN MONTH(ObsHour) >= 7
                    THEN YEAR(ObsHour) ELSE YEAR(ObsHour) - 1 END) PERSISTED,
ObsDate         AS (CONVERT(date, ObsHour))    PERSISTED,
ObsHourOfDay    AS (DATEPART(hour, ObsHour))   PERSISTED
```

`ObsHour` is **local time at the resort** (`timezone=auto` on the fetch).

- `PK_HourlyObs PRIMARY KEY CLUSTERED (ResortId, ObsHour)`
- `IX_HourlyObs_Date (ObsDate, ResortId)`, `IX_HourlyObs_Season (SeasonStartYear, ResortId)`
- CHECKs: `TempF BETWEEN -100 AND 130`, `SunshineSec BETWEEN 0 AND 3600`,
  cloud percentages `0..100`, and `SnowfallIn/SnowDepthFt/RainIn >= 0`
- FKs to `ref.Resort` and `ref.WeatherCode`

### `meteo.SkiDay`

`PK_SkiDay PRIMARY KEY CLUSTERED (ResortId, ObsDate)`,
`IX_SkiDay_Season (SeasonStartYear, ResortId) INCLUDE (IsGood, IsGreat)`,
`IX_SkiDay_Date (ObsDate)`.

Columns, in insert order:

```
ResortId, ObsDate, SeasonStartYear, LiftHours,
ModelBaseFt, ModelOvernightIn, ModelDaySnowIn,
ModelSnow72In, ModelSnow24In, ModelSnow168In,
DayRainIn, RainOnSnow,
MeanTempF, MinTempF, MaxTempF,
MeanApparentF, MinApparentF, MaxApparentF, WindChillGapF,
SunFraction, OpaquePct, FlatLightHours, BluebirdHours,
MaxGustMph, MeanGustMph, WindHoldHours,
IsCovered, IsFreshModel, IsFreshMeasured, FreshSource, IsFresh,
SnotelSwe72In, SnotelNewSnow72In, SnotelNewSnow24In, SnotelNewSnow168In,
SnotelBaseFt, BaseSource,
IsGood, IsGreat, IsEpic, FailReason, FailMask
```

`IsFresh*` now means **2 inches in 24 hours** -- the line Great's second path
tests -- rather than the retired 80th-percentile fresh line, so the kappa h20
prints on the cards answers the question the tiers actually ask. `IsFreshModel`
is what ERA5 thinks; `IsFreshMeasured` is what the gauges measured, `NULL` where
there are none. `IsFresh` is the one the tiers use and it defers to measurement
wherever it exists. The model's own verdict is kept so the
h20 validation compares ERA5 to the gauges rather than the gauges to themselves.

## 6. The 27 variables — the load-bearing invariant

```
temperature_2m, apparent_temperature, snowfall, snow_depth, rain,
cloud_cover, cloud_cover_low, cloud_cover_mid, cloud_cover_high,
weather_code,
wind_direction_100m, wind_direction_10m, wind_speed_100m, wind_speed_10m,
wind_gusts_10m, dew_point_2m, relative_humidity_2m, sunshine_duration,
direct_normal_irradiance, diffuse_radiation, shortwave_radiation,
terrestrial_radiation,
direct_normal_irradiance_instant, diffuse_radiation_instant,
shortwave_radiation_instant, terrestrial_radiation_instant,
is_day
```

**This order appears in three places and they are coupled positionally, because
`BULK INSERT` is positional:**

```
h01_fetch.py:VARS  ≡  h02_shred.py:VARS  ≡  stg.HourlyRaw columns (h01_schema.sql)
```

Change one without the other two and every column after the change point loads
into the wrong field, silently and with plausible-looking values.

Two traps:

1. **The field is `terrestrial_radiation`, not `terrestrial_solar_radiation`.**
   Both endpoints reject the latter.
2. **No unit conversion happens anywhere.** The fetch URL asks for
   `temperature_unit=fahrenheit`, `wind_speed_unit=mph`,
   `precipitation_unit=inch`, so Open-Meteo returns °F / mph / inch / ft
   directly. `h02_shred.py` only *validates* the returned units against its
   `EXPECTED_UNITS` dict and exits on a mismatch. There is no °C→°F or mm→in
   arithmetic in Python or SQL, and adding any would double-convert.

### Fetching (only if the JSON is lost)

`h01_fetch.py`, against `https://archive-api.open-meteo.com/v1/archive`
(or `customer-api...` with a key, or `--local` for a self-hosted instance).

- **`elevation` is mandatory.** Without it Open-Meteo answers on its own grid
  cell — 3062 m for Snowbird against a real 2859 m summit. The elevation is
  formatted `%.4f`, not `%g`, because `%g` rounds to six significant figures and
  would make new files disagree with `_hourly_meta.txt`.
- Budget: `weight = (n_vars/10) × (days/14)`. 27 variables over the full range is
  ~1,902 units per resort; all 431 is ~820,000 units, roughly **82 days** on the
  free tier. `_fetch_state.json` holds a rolling 24-hour spend log.
- Downloads stream to `<dest>.part` and `os.replace()` into place, so a partial
  file is never left under the real name. Existing files are verified (hour
  count, all variables present, elevation match) and skipped.
- `--jobs > 1` requires `--local`/`--host` or an API key. Workers are handed
  geo-sorted contiguous bands so consecutive requests hit server-side cache —
  measured 654 s cold against 2 s for a warm neighbour.

### Filenames

`safe_stem()` replaces Windows-illegal characters with `-`, and `STEM_ALIAS`
pins two historical names:

```python
STEM_ALIAS = {'Showdown Montana - MT': 'Showdown - MT',
              'Whitefish Mountain - MT': 'Whitefish - MT'}
```

`h01_fetch.py` and `h02_shred.py` must keep identical copies of both.
`h02_shred.py` builds its filename→resort index **forwards** (derive the expected
filename from each known resort name) and resolves every file before shredding
begins. The old backwards rule — exact match, then unique prefix — could not
handle `Boston Mills/Brandywine - OH`, whose slash becomes `-`.

## 7. The model — `sql/h05_skiday.sql`

The heart of the project. It owns `meteo.usp_BuildSkiDay`, `meteo.vSkiDay` and
`meteo.vSkiDaySnow`, and it drops and recreates `meteo.SkiDay` and
`meteo.ResortBenchmark` on every run.

Rewritten 2026-09-08. Every axis changed: new temperature bands, a sky scale in
opaque cloud rather than sunshine hours, wind on duration rather than one gust
hour, and snow on absolute inches across three windows instead of a 72-hour
percentile.

### Parameters

```sql
@OpenHour       int   = 9      -- first lift hour, local
@CloseHour      int   = 15     -- last lift hour (15 = through 15:59)
@MinApparentF   float = 16.0   -- Chilly floor; below it the day is Meh
@MaxApparentF   float = 45.0   -- above this it is slush
@ComfortMinF    float = 20.0   -- Comfortable floor; gates the cloudy days
@GustHoldMph    float = 40.0
@FlatLightPct   int   = 80
@BluebirdPct    float =  5.0   -- the six opaque-cloud bands
@SunnyPct       float = 12.5
@MostlySunnyPct float = 37.5
@MostlyCloudPct float = 62.5
@CloudyPct      float = 87.5
@EpicMinF       float =  8.0   -- EPIC's own floor: the bottom of Very Cold
@Snow24GreatIn  float =  2.0   -- measured inches; the model side is
@Snow24EpicIn   float =  4.0   -- bias-corrected per resort, see below
@Snow72In       float =  5.0
@Snow168In      float =  5.0
@MinRealBaseFt  float =  0.5
@FallbackBias   float =  0.65  -- DEPTH ratio only
```

### The bands

| felt temperature | °F | | opaque sky cover | |
|---|---|---|---|---|
| Bitter Cold | under 8 | | Bluebird | ≤ 5% |
| Very Cold | 8–15 | | Sunny | 5–12.5% |
| Chilly | 16–19 | | Mostly Sunny | 12.5–37.5% |
| Comfortable | 20–32 | | Partly Sunny | 37.5–62.5% |
| Warm | 33–45 | | Mostly Cloudy | 62.5–87.5% |
| Very Warm | over 45 | | Cloudy | > 87.5% |

Flat light overrides all six sky bands and is unchanged: low cloud ≥ 80% over
more than half the lift hours.

### The tiers

```
BASE  = App 16..45  AND NOT flat light
                    AND WindHoldHours <= LiftHours/2
                    AND NOT rain-on-snow

GOOD  = BASE AND (OpaquePct <= 62.5 OR App >= 20)

GREAT = SAFE AND Snow168 >= 5" AND (
          (App 20..45 AND OpaquePct <= 37.5)                  -- nothing fresh
       OR (App  8..45 AND CLOUDCLAUSE AND Snow24 >= 2")       -- 2 inches this morning
       OR (App  8..45 AND CLOUDCLAUSE AND Snow72 >= 5")       -- 5 over three days
        )

  where CLOUDCLAUSE = (OpaquePct <= 62.5 OR App >= 20), Good's own

EPIC  = SAFE AND App 8..45                   -- NOT Good: its own floor
             AND (App >= 16 OR OpaquePct <= 62.5)   -- Very Cold needs Partly Sunny+
             AND Snow168 >= 5" AND Snow24 >= 4"

  where SAFE = NOT flat light AND NOT wind hold AND NOT rain-on-snow
```

**One sky rule, not three.** Every tier is built on GOOD and adds no sky test of
its own except on the no-new-snow path, where the sky is the entire reason the
day qualifies. The tighter gate the snow paths used to carry (`<= 37.5`, and
`<= 12.5` before that) was a fourth rule doing work three others already did:
flat light rejects the days you cannot see, the 16 °F floor rejects the ones you
cannot bear, and GOOD's own clause rejects cold under heavy cloud. On top of
those it was discarding **a third of all 4-inch mornings** — 16.4 inches of
gauge-measured snow at 18 °F at Heavenly on 2006-04-17 ranked *Good* — because
Chilly is one degree short of Comfortable and 46% cloud is past Mostly Sunny.

**Nothing nests.** Great's 24-hour branch reaches to 8 °F where Good stops at
16 °F, so **9,116 days are Great without being Good** — 4,584 of them already
Epic, 4,532 presently Meh. The three flags are three separate verdicts; only the
display orders them, as `epic ? 3 : great ? 2 : good ? 1 : 0`. Anything treating
one as implying another is wrong.

**Both snow branches share the 8 °F floor.** The 72-hour branch kept 16 °F for a
single build, and the asymmetry that produced was the argument against it: 9,865
Very Cold days had five inches down over three days, no 2-inch morning, and were
rejected while thinner days were taken. Only branch 1 keeps a higher floor, and
it has to — nothing fresh has fallen, so comfort and sun are the entire case for
the day.

**18,977 days are Great without being Good**, a fifth of all Great days. Good's
flat 16 °F floor is what both snow branches route around; each widening of them
widens that gap rather than closing it.

**Epic deliberately does not.** It is not the top rung of the ladder; it is a
separate verdict about the snow, answering "was this a powder day you could
ride" rather than "was this a nice day". So it accepts two kinds of day Good
rejects — **7,293 across the record**, and they are the biggest days in it:

| Epic but not Good | days | why Good says no |
|---|---|---|
| Very Cold, 8–15 °F | 4,586 | the 16 °F floor is a *comfort* line |
| Chilly under heavy cloud | 2,707 | Good wants Comfortable past 62.5% cloud |

Taos on 2005-02-27 had **37 inches** of gauge-measured snow at 12 °F under a 36%
sky and scored Meh on a `FailMask` of 8 — one bit, too cold, nothing else wrong.
The whole Tahoe basin sat under 30 inches at 10–14 °F on 2023-01-01, all Meh.

The **cold ladder is monotone**, which is the property worth checking: Bitter
Cold never qualifies, Very Cold must be Partly Sunny or better, Chilly and up
need no sky at all. The colder the day, the more light it must be given before
snow can carry it.

Anything treating the three flags as a ladder must read **Epic first** — which
every consumer already does, since a day's tier is `epic ? 3 : great ? 2 : good ? 1 : 0`.

### The five ideas that make it defensible

**1. Every snow test is an absolute depth, never a percentile.** This is the
whole ranking. A per-resort percentile ranks each mountain against itself, so it
hands every one of them the same quota of big-snow days however little it snows.
Mt. Lemmon averages 10.7 inches for an entire season, and its 94.9th-percentile
24-hour cut computes to **0.17 inches** — under which it scored more Epic days
than Alta or Mt. Baker. Absolute inches drop it to 0.04.

**2. The model side is bias-corrected, not percentile-matched.** Resorts with a
gauge are tested on the gauge. The 33 without one are tested on modelled inches
against `ResortBenchmark`, which holds the same inch figures converted to that
resort's own modelled scale. **Two separate snowfall ratios** (24 h and
168 h -- one per window a tier tests), median of the gauged resorts as the
fallback. None of them is `@Bias`,
which is a *depth* ratio. Modelled snowfall is not uniformly low — Alta reads
about 0.68 of its gauges, Mt. Baker about 1.53 — which is exactly why one flat
model-inch threshold cannot work.

**3. Wind is tested on gusts, not sustained speed, despite the prose.** ERA5's
10 m wind is a ~25 km grid-cell mean: across 4.4 million lift hours it averages
5.3 mph and touches 40.0 mph exactly once, so a sustained-40 rule would never
fire in 27 winters. The gust field (mean 20.3, max 136) is the one carrying
mountain wind. What did change is the duration: gusts over **half** the lift day
rather than a single hour, which fires on 4.9% of days against 9.5%.

**4. Opaque cloud excludes high cirrus.** `OpaquePct` is the mean over lift hours
of the *greater* of the low and mid layers — the greater, not the sum, because
the layers are stacked and a sum can exceed 100%. Counting cirrus would read 38%
of all Dec–Apr days as fully cloudy against 25% without it.

**5. `OpaquePct` is quantised once, before the tiers.** Rounded to the same
2-point grid the page ships, so the tier test, the band label and the printed
percentage are one number. Ship it finer than you test it and a day reads
"Mostly cloudy, 88%" against an 87.5 boundary. The sun test had this exact bug
and was fixed the same way.

**Base is reported, not tested**, unchanged from before: `IsCovered` survives as
a column but gates nothing, because neither ERA5 nor SNOTEL can see snowmaking.

### FailReason and FailMask

`FailReason` names the **first** thing wrong, in priority order: **epic or
great** → rain on snow → wind hold → flat light → too cold → too warm → cloudy
and cold → no week snow → no fresh snow → grey → `'Great'`.

**Epic and Great sit at the head of the chain**, and that one row carries both
waivers the rules ask for (`Too Cold ... AND not EPIC`, `Cloudy and Cold ... AND
not EPIC`): neither tier is ever labelled Meh. Great joined Epic there when its
24-hour branch was allowed down to 8 °F — without it, 4,532 days the tiers call
Great would carry `'Too cold'` and be counted as such in the failure panel. The
rules except only EPIC, but `FailReason` answers *why is this day not Great*, so
for a day that **is** Great the answer can only be nothing. It maps to `'Great'`, this list's index-0
sentinel meaning *nothing went wrong* — not a claim the day was Great, which a
Very Cold Epic day is not. Without the row such a day falls through every test
and lands on `'Grey'`, which says "too much cloud" about days that are Bluebird
as often as not.

`FailMask` is **not** waived for Epic days: it is the factual record of which
Good-tier tests failed, and an Epic day at 12 °F did fail the 16 °F one. The page
renders it only on Meh days, so the difference never reaches a reader.

**`'Grey'` is unreachable** and kept only so the packed reason indexes do not
shift. It fired when a day had the snow and the cold but too much cloud — exactly
the case the tiers above stopped rejecting. A Good day that holds the week and is
not Great now always lacks fresh snow, so `'No fresh snow'` catches every one.
The ordinal array in `h07_pack.py`, `h07_build.py`, `_hscript.js` and both
verifiers must keep the slot regardless.

`FailMask` is every Good-tier test the day failed, as bit flags:

```
 1  rain on snow     8  too cold
 2  wind hold       16  too warm
 4  flat light      32  cloudy and cold
```

The bits were **renumbered** in this rewrite — the long-retired thin-base slot is
finally reclaimed. That is only safe because the whole payload regenerates from
this table on every build, so there are no archived days to relabel; the packer,
the page and `_hverify.js` must move in the same commit.

`MissMask` answers the question one tier up — what a day that **cleared** its
tier fell short of on the next:

```
 1  no 5-inch week                                           (a Good day)
 2  nothing fresh, and not sunny and comfortable without it  (a Good day)
 4  under 4 inches this morning                              (a Great day)
```

Bits 1–2 are set only on Good days and bit 4 only on Great days, so the tooltip
renders the right row from the tier alone. Bit 4 needs no test of its own: a
Great day already holds the week and Good's sky clause, so the morning is the
only thing between it and Epic. Epic sets nothing.

## 8. The SNOTEL layer

The least obvious part of the system, because the numbers live in two different
places.

**The 35 km gate is in `h19_snotel_all.py`, not in SQL:**

```python
BASE = 'https://wcc.sc.egov.usda.gov/awdbRestApi/services/v1'
RADIUS_KM, FALLBACK_KM, MIN_STATIONS = 35.0, 60.0, 3
```

Every station within 35 km, extended to 60 km where fewer than three are in
range. `h20_snotel_all.sql` takes every row of `_snotel_map_all.txt` as given and
applies no radius filter of its own.

### Ranking

`StationRank` = nearest first. `ElevRank` = closest to mid-mountain elevation,
ties broken by distance. **Snow uses the neighbourhood; base uses the
elevation-matched station** — snowfall averaging barely cares about distance, but
depth is elevation-sensitive.

### The consensus

Each station's 72-hour water gain is divided by **that station's own 80th
percentile** before averaging across the neighbourhood:

```sql
Own80 = PERCENTILE_DISC(0.80) WITHIN GROUP (ORDER BY s.Swe72In)
        OVER (PARTITION BY x.ResortId, x.Triplet)
...
Composite = AVG(CASE WHEN n.Own80 > 0 THEN n.Swe72In / n.Own80 END)
```

So `Composite` is expressed in multiples of a normal big dump *at that place*,
not in inches. Independent sensor noise averages out; the real weather signal
does not.

Day-over-day steps clip negatives to zero (melt and settling are not negative
snowfall) and require `DATEDIFF(day, PrevDate, ObsDate) = 1`, so a reporting gap
is never read as a multi-day dump.

### Scoring

`meteo.SnotelBenchmark` builds a 2×2 table of model-fresh against gauge-fresh
over Dec–Apr and derives Recall, Precision, Agreement and Kappa. The join carries
a **one-day offset** (`c.ObsDate = DATEADD(day, -1, d.ObsDate)`) because the
model's window ends at the lift opening while a SNOTEL daily value ends at local
midnight.

## 9. Payload encoding

The part with the least margin for error.

A 92-character alphabet, chosen to contain **no `"` and no `\`** so the payload
needs no escaping:

```
0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz!#$%&()*+,-./:;<=>?@[]^_{|}~'`
```

Each resort carries one string per season, Dec 1 → Apr 30, at **19 characters per
day**. An absent day is 19 spaces. (This read "17" until 2026-09-19, two slots
after it stopped being true — the table below is the authority.)

| Slot | Content |
|---|---|
| 0 | tier in bits 0–1, week verdict in bit 2, `MissMask` in bits 3–5 (0–63) |
| 1 | felt mean, absolute, window `TMIN,TMAX = -33,58` |
| 2 | sun fraction × 90 (reported only; gates nothing) |
| 3 | peak gust, mph, capped at 90 |
| 4 | modelled **week** snow as a multiple of this resort's 5″ line, 0–3× → 0–90 |
| 5 | measured week snow, **whole inches** capped at 91, or space |
| 6 | fail reason index |
| 7 | sky band index (7 values: flat light + six opaque bands) |
| 8 | degrees below the felt mean |
| 9 | degrees above the felt mean |
| 10 | measured new snow, 72 h, inches |
| 11 | measured water, 72 h, inches × 10 |
| 12 | measured new snow, 24 h, inches |
| 13 | fail mask |
| 14 | **air temp as a gap off the felt mean**, bias `GAPMIN = -20` |
| 15 | degrees below the air mean |
| 16 | degrees above the air mean |
| 17 | opaque cloud percent ÷ 2 (0–50) |
| 18 | modelled 24 h snow as a multiple of this resort's 2″ line, 0–3× → 0–90 |

**Air temperature rides as an offset, not on a window of its own, and this is
forced rather than preferred.** `MeanTempF` spans −51.5 to 76.5 °F — a 128°
range that does not fit 92 values, so an absolute window would clamp real days at
both ends. The wind-chill gap spans −1 to 19. Measured across all 628,936 shipped
days: **zero clamps** on any of the three temperature fields.

**`r0()` — half away from zero — is used for every quantised field**, not just
temperature. Python rounds halves to even, so `14.5` packs as `14` while SQL,
which rounds half up, tests `15`. That split put 640 of 114,352 values one step
off and produced labels that contradicted the numbers beside them.

### The second positional invariant

The day-field order is coupled across four files:

```
sql/h14_export.sql  ≡  h07_pack.py:DAY_COLS
                    ≡  _hscript.js:decode()
                    ≡  _hverify.js:COLS
```

**New columns are appended to the end, never inserted in the middle.** Inserting
`IsEpic` mid-list once shifted every later index by one and silently zeroed the
snow bars. `h07_pack.py` reads by name from `DAY_COLS` rather than by raw index
for the same reason.

`_hverify.js` is the guard: it lifts `decode()` **out of the shipped
`_hscript.js`** and compares every decoded field back to the SQL export.
Currently 628,936 days × 17 fields = **10,691,912 comparisons, 0 mismatches**.
It is the check that catches both failure modes this pipeline has actually
shipped — positional drift, and a rounding rule that differs between packer and
page.

## 10. The page

`h15_build.py` splices three pieces: the shell of `seven_hours.html` up to its
`<script>` tag, the payload, and `_hscript.js`.

- The payload is injected as **`JSON.parse("...")`, not a JS object literal.**
  The engine parses a 12 MB object literal as source in 147 ms; the same bytes
  through `JSON.parse` take 14 ms.
- A **control-character guard** rejects the built page if any character below
  U+0020 other than tab/CR/LF appears. A mangled CSS escape once wrote a literal
  NUL that the browser drew as a replacement glyph mid-card.
- **16 MB is a hard refusal** (the published-artifact ceiling); 12 MB prints a
  warning.

### Front-end

Region multi-select chips; state, vertical, terrain, name and **year-range**
filters; three tier sorts plus two price sorts; a trip window with ±0/2/4/7 days
of context padding; a per-day tooltip; and a fail-mix panel recomputed from the
packed reason characters for the selected years.

`METAFMT` maps 17 `data-meta` attributes to formatters reading `_hmeta.json`.
**Every figure the page states about itself is generated.** Typed counts were
correct the day they were typed and silently wrong every day after — the page
once claimed "93–100% of days" when the real figure was 74%.

### The editorial cuts

Two settings decide which resorts appear, and both are editorial choices, not
missing data:

- `@MinVerticalFt = 899` — 230 resorts. 899 rather than 900 is deliberate:
  Mount Bohemia is exactly 900 ft and is a genuine destination, so the cut sits
  one foot below it rather than at a rounder number that would drop it.
- `@Regions` — seven western regions, taking 230 down to **154**.

To restore all 230: set `@Regions = N''` in all three h14 batches and run
`--export-only`. Note that at 17 characters per day the 230-resort build lands
near **15.3 MB** — inside the 16 MB cap, but with little room left.

| Question | Answer | Evidence |
|---|---|---|

## 14. The hosted build

`run_pipeline.py --web` produces a second, independent target from the same
model and the same export SQL. Nothing it does touches the artifact build.

```
h14_export.sql  -v AllResorts=1   ->  _skidays_all.txt / _resorts_all.txt / _meta_all.txt
h07_build.py                      ->  web/index.json + web/day/<slug>.json  (431 files)
_wverify.js                       ->  every value vs SQL, by name, streaming
h15_web.py                        ->  web/index.html + web/app.<hash>.js
```

| | artifact | hosted |
|---|---|---|
| resorts | 154 | **431** |
| encoding | 19 packed alphabet chars/day | 1 index char + columnar JSON |
| first paint | 11.7 MB (the whole file) | **587 KB gzip** (index only) |
| detail | inlined | ~36 KB gzip per resort, fetched on view |

**Why the encoding differs.** Measured on this dataset, gzipped: the packed
alphabet is 6.69 MB, columnar JSON is 6.04 MB. The packing is 10% *worse* over
the wire and only ever won on raw bytes, which matters solely because an
artifact ships uncompressed. It stays in the artifact build because there it is
the only way 154 resorts fit under 16 MB.

**`$(AllResorts)`** picks the coverage, as an sqlcmd `-v` **integer**: sqlcmd 16
rejects a `-v` value containing a space, and every region name has one. Both
cuts stay defined in the SQL, once per batch.

**`_hscript.js` serves both.** It switches on `window.WEBBUILD` and asks
`bitsAt()` / `dayAt()` for a day; everything that ranks, filters or counts uses
`bitsAt()` and never waits on the network. The hosted shell fetches the index,
puts `DATA`/`META` on `window`, then loads the script — which is why the
script's initialisation needed no restructuring at all.

**Plots are built on view, in both builds.** `render()` draws every card that
passes the filters, and at 431 resorts that was 174,555 cells and a measured
**13.7 seconds** for one re-sort. Deferring the grid to an `IntersectionObserver`
took it to **0.8 s**, with ~1,200 cells in the DOM instead of 174,555. The same
observer prefetches the resort's detail file, so a tooltip rarely waits.

**Serving it.** Gzip on `.json` and `.js` is not optional — every figure above
assumes it. `app.<hash>.js` is content-fingerprinted; `index.json` is fetched
`no-cache` because it changes on every rebuild and its URL does not.

**Still to do:** the fonts are still Google-hosted (§10 of the plan), and there
is no deploy config or cache-header setup for a specific host.

## 15. Verifying a rebuild

1. **`_hverify.js` must report `MISMATCHES: 0`.** It decodes the shipped payload
   with the page's own `decode()` and compares every field to the SQL it came
   from. This is the single most valuable check in the project; it has caught
   both bugs that ever reached the built page.
2. **`h07_pack.py`'s drift assertion** must pass — the resort-card count and the
   meta row must agree.
3. **`h15_build.py`** must print a size under 16 MB and emit no control-character
   error.
4. **Rendering is not optional.** Three of the last several bugs — a grid
   overflow, an `auto-fit` track stretching a single filtered result to 1192 px,
   and slack distributed by `align-content: stretch` — were invisible to every
   assertion and only appeared on screen.

Expected timings: full `--all` rebuild ~86 min; `--export-only` ~0.7 min;
`h05_skiday.sql` alone ~7.8 min; `h20_snotel_all.sql` ~0.5 min.
